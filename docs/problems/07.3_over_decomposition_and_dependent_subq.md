# Problem 05: Over-decomposition and dependent sub-questions

**Date:** Sept 14, 2026
**Where seen:** `docs/outputs/07_analysis_100q.txt`, naive-wins samples

## Observation A: Over-decomposition

Question: "What is the name for the adventure in 'Tunnels and Trolls', 
a game designed by Ken St. Andre?"

HopSense produced 3 sub-questions:
1. What is 'Tunnels and Trolls'?
2. Who is Ken St. Andre?
3. What is the name of the adventure designed by Ken St. Andre for 
   'Tunnels and Trolls'?

Sub-question 3 is almost identical to the original. Sub-questions 
1 and 2 add no useful hops — they retrieve background info that 
doesn't answer the actual question. Meanwhile, none of them retrieved 
"Arena of Khazan" specifically.

Result: HopSense returned UNKNOWN. Naive got it right.

## Observation B: Dependent sub-questions

Question: "What is the middle name of the actress who plays Bobbi Bacha 
in Suburban Madness?"

HopSense produced:
1. Who plays Bobbi Bacha in Suburban Madness?
2. What is the middle name of the actress identified in the first question?

Sub-question 2 is *ungrounded* when retrieved in isolation — it 
references "the actress identified in the first question" but the 
retriever has no memory of what sub-question 1 answered. Vector 
search on "the middle name of the actress identified in the first 
question" retrieves nothing useful.

## Why both happen

The decomposer prompt says "break into atomic sub-questions" but 
does not enforce that:
(a) each sub-question must be independently retrievable, or
(b) the number of hops matches the true depth of the question.

Bridge questions with entities named in the query only need one 
hop *per entity*. The decomposer sometimes adds a wrapping "what is 
this whole question about" hop that adds nothing.

## Options

1. **Stricter decomposer prompt:** "Each sub-question must be 
   answerable on its own using no context from other sub-questions." 
   Cheap.
2. **Chained execution:** After answering sub-question 1, feed the 
   answer *into* sub-question 2's retrieval query. This actually 
   implements multi-hop reasoning properly (ReAct-style).
3. **Cap sub-questions at 2** for now. Force the model to pick the 
   two most essential atomic questions.

## Decision

Do option 1 immediately (cheap). Implement option 2 next milestone — 
it's the more principled fix and closer to how real multi-hop 
reasoning should work. Option 3 as a fallback if option 1 doesn't 
help.

## Takeaway

Naive decomposition isn't enough. Real multi-hop retrieval needs 
either (a) fully independent sub-questions, or (b) chained execution 
where later hops consume earlier answers. Static "independent" 
decomposition is the worst of both worlds when the questions are 
actually sequential.

## Update (Sept 14, 2026): M6 attempt — stricter prompt

Tried Option 1 (stricter decomposer prompt) as M6. Added explicit rules 
against wrapper sub-questions and back-references ("the actress identified 
in the previous question").

Result on same 100 questions:

| | Baseline (M5) | After M6 | Δ |
|---|---|---|---|
| Naive contains-gold | 40% | 40% | 0 |
| **HopSense contains-gold** | 58% | 54% | **-4 pp** |
| Naive-wins count | 6 | 7 | +1 |
| Both-wrong count | 36 | 39 | +3 |

The stricter prompt did NOT fix the failure. The "Bobbi Bacha middle 
name" case still produced sub-question "What is the middle name of the 
actress identified in the previous question?" — verbatim, despite the 
explicit rule against back-references.

### Why prompt engineering hit a wall

GPT-4o-mini's decomposer treats atomic multi-hop questions as inherently 
sequential — it *knows* the second hop depends on the first, and 
generating an "independent" version of a genuinely dependent question 
is not possible without introducing false context.

### Decision

Rollback M6. The real fix is **chained execution** (Option 2 in this 
problem file): feed sub-question 1's answer INTO sub-question 2's 
retrieval query. That is a full architectural change, deferred to a 
later milestone.


### Takeaway

Some multi-hop failures don't respond to decomposer prompt tweaks. 
The failure looks architectural: static decomposition + independent 
retrieval can't cleanly handle genuinely sequential questions. This 
points at chained (ReAct-style) execution as an architectural choice 
worth trying, not just an optimization.
